# Arquitetura Cloud Solutions & Scalable Infrastructure

Este documento apresenta a arquitetura de infraestrutura utilizada pela aplicação, seus principais componentes, o fluxo de dados e as estratégias adotadas para escalabilidade, segurança, observabilidade e recuperação.

A solução utiliza serviços gerenciados da Microsoft Azure para executar a API, armazenar dados, disponibilizar a aplicação e centralizar o monitoramento. A aplicação é desenvolvida em Python com FastAPI e executada em um container Docker hospedado no Azure Container Instances.

## Visão geral da arquitetura

A aplicação recebe requisições HTTP REST de clientes externos, como usuários ou ferramentas de teste como Postman. As requisições são direcionadas para a API FastAPI executada em uma instância do Azure Container Instances.

A API é responsável pela ingestão dos dados, geração de previsões e consulta dos resultados. Para persistência, utiliza Azure Database for MySQL. Os arquivos CSV e logs são armazenados no Azure Blob Storage, enquanto Azure Monitor, Application Insights e Log Analytics são utilizados para observabilidade.

```text
Cliente
   │
   │ HTTP REST
   ▼
Azure Container Instances
   │
   ├── FastAPI
   │   ├── POST /ingerir
   │   ├── GET /prever
   │   ├── GET /previsoes
   │   └── GET /health
   │
   ├──────────────► Azure Blob Storage
   │                 CSVs e logs
   │
   ├──────────────► Azure Database for MySQL
   │                 Dados e previsões
   │
   └──────────────► Azure Monitor
                     Application Insights
                     Log Analytics

              Azure Virtual Network
```

A comunicação entre os componentes internos ocorre por meio da infraestrutura de rede da Azure, enquanto o acesso público é disponibilizado exclusivamente pela API.

## Componentes da solução

### Azure Container Instances

O Azure Container Instances, ou ACI, é responsável pela execução da aplicação em um container Docker gerenciado pela Azure.

A aplicação utiliza Python 3.9, FastAPI e Gunicorn. O Gunicorn executa quatro workers utilizando `UvicornWorker`, permitindo o processamento concorrente de requisições HTTP.

A imagem Docker utiliza `python:3.9-slim` como base e possui aproximadamente 400 MB.

A aplicação é iniciada com:

```bash
gunicorn app:app --workers 4 --worker-class uvicorn.workers.UvicornWorker
```

A configuração atual da instância é:

```text
CPU: 1 vCPU
Memória: 1 GB
Porta: 8000
Ambiente: variáveis de configuração e secrets
```

A aplicação disponibiliza os seguintes endpoints:

| Método | Endpoint     | Responsabilidade               |
| ------ | ------------ | ------------------------------ |
| `POST` | `/ingerir`   | Recebe e processa arquivos CSV |
| `GET`  | `/prever`    | Gera previsões para D+1 e D+7  |
| `GET`  | `/previsoes` | Consulta previsões armazenadas |
| `GET`  | `/health`    | Verifica a saúde da aplicação  |

### Azure Database for MySQL

O Azure Database for MySQL é utilizado como camada de persistência da aplicação. O banco armazena os resultados das previsões e os registros de auditoria das operações realizadas.

A configuração atual é:

```text
Servidor: mysql-nexusops-8929.mysql.database.azure.com
Versão: MySQL 8.0.32
Tier: Basic
CPU: 1 vCore
Storage: 50 GB
Database: db_nexusops
```

O schema principal é composto pelas tabelas `tb_previsoes` e `tb_auditoria`.

```sql
CREATE TABLE tb_previsoes (
    id INT PRIMARY KEY AUTO_INCREMENT,
    data_previsao DATETIME,
    d_plus_1 FLOAT,
    d_plus_7 FLOAT,
    registros_ingeridos INT,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tb_auditoria (
    id INT PRIMARY KEY AUTO_INCREMENT,
    operacao VARCHAR(50),
    qtd_registros INT,
    status VARCHAR(20),
    mensagem TEXT,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

A conexão utiliza SSL/TLS e o acesso ao banco deve ser restrito aos componentes autorizados da aplicação. Credenciais sensíveis não devem ser armazenadas diretamente no código ou no repositório.

### Azure Blob Storage

O Azure Blob Storage é utilizado para armazenamento de objetos, principalmente arquivos de entrada, arquivos processados e logs.

A estrutura utilizada é:

```text
stchallengelw26/
├── raw/
│   └── incidentes.csv
├── processed/
│   └── incidentes_processados.csv
└── logs/
    ├── app-2026-08-20.log
    └── errors-2026-08-20.log
```

O diretório `raw` concentra os arquivos recebidos pela aplicação. O diretório `processed` armazena arquivos após o processamento, enquanto `logs` concentra registros relacionados à execução da aplicação.

Quando configurado com redundância geográfica, o armazenamento também pode oferecer maior proteção contra indisponibilidade regional.

### Azure Container Registry

O Azure Container Registry, ou ACR, mantém a imagem Docker utilizada pela aplicação.

A configuração atual é:

```text
Nome: acrnexusops8929
Região: Norway East
SKU: Standard
Autenticação: Admin habilitado
```

O processo de publicação segue o fluxo:

```text
Dockerfile
    │
    ▼
Docker Build
    │
    ▼
Azure Container Registry
    │
    ▼
Azure Container Instances
```

Essa separação permite manter a imagem versionada no registry e reutilizá-la durante novos deployments.

### Azure Monitor, Application Insights e Log Analytics

A camada de observabilidade é composta pelo Azure Monitor, Application Insights e Log Analytics.

O Azure Monitor acompanha métricas de infraestrutura, como CPU, memória e operações de I/O. Também pode ser utilizado para criação de alertas relacionados ao comportamento da aplicação.

O Application Insights fornece observabilidade sobre a aplicação, incluindo requisições HTTP, latência, exceções, erros, dependências externas e eventos personalizados.

O Log Analytics centraliza os registros e permite consultas utilizando Kusto Query Language, conhecida como KQL.

Essa camada permite acompanhar tanto a infraestrutura quanto o comportamento da aplicação sem depender exclusivamente dos logs locais do container.

## Rede e conectividade

A infraestrutura utiliza uma Virtual Network dedicada para organizar a comunicação entre os componentes.

A topologia planejada é:

```text
VNet: vnet-nexusops
CIDR: 10.0.0.0/16

├── subnet-app
│   CIDR: 10.0.1.0/24
│   └── Azure Container Instances
│
└── subnet-data
    CIDR: 10.0.2.0/24
    └── Azure Database for MySQL
```

A separação entre as subnets permite aplicar regras específicas de comunicação e reduzir a exposição dos componentes internos.

O objetivo é manter o banco de dados acessível somente pelos componentes necessários, evitando exposição direta à Internet.

## Fluxo de dados

### Ingestão de dados

A ingestão começa quando o cliente envia um arquivo CSV para o endpoint `POST /ingerir`.

A aplicação valida a estrutura do arquivo, processa os registros e persiste os resultados no banco de dados. Ao final da operação, um registro de auditoria é criado e as informações relevantes são registradas nos logs.

```text
POST /ingerir
      │
      ▼
Recebimento do CSV
      │
      ▼
Validação
      │
      ▼
Processamento dos registros
      │
      ├──────────────► tb_auditoria
      │
      ├──────────────► tb_previsoes
      │
      └──────────────► Blob Storage
                       Logs
      │
      ▼
Resposta HTTP
```

Uma resposta de sucesso possui o seguinte formato:

```json
{
  "status": "OK",
  "registros": 30
}
```

### Geração de previsões

A geração de previsões é realizada pelo endpoint `GET /prever`.

A aplicação carrega o modelo de machine learning, consulta os dados mais recentes armazenados no banco e executa a previsão para os horizontes D+1 e D+7.

```text
GET /prever
      │
      ▼
Carregamento do modelo
      │
      ▼
Consulta aos dados recentes
      │
      ▼
Execução do modelo ML
      │
      ▼
Previsão D+1 e D+7
      │
      ├──────────────► tb_previsoes
      │
      └──────────────► Application Insights
      │
      ▼
Resposta HTTP
```

Exemplo de resposta:

```json
{
  "d_plus_1": 894.51,
  "d_plus_7": 963.83
}
```

### Consulta de previsões

O endpoint `GET /previsoes` consulta os resultados mais recentes armazenados no banco.

A aplicação executa uma consulta equivalente a:

```sql
SELECT *
FROM tb_previsoes
ORDER BY criado_em DESC
LIMIT 10;
```

Os registros são serializados para JSON e retornados ao cliente.

## Escalabilidade

A arquitetura permite evolução tanto vertical quanto horizontal, embora a capacidade efetiva dependa das características e limitações dos serviços utilizados.

Na escala vertical, a aplicação pode receber mais CPU e memória, enquanto o banco pode ser migrado para uma camada de maior capacidade.

Na escala horizontal, múltiplas instâncias da aplicação podem ser utilizadas atrás de um componente responsável pela distribuição das requisições.

```text
                    Load Balancer
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
            ACI         ACI         ACI
             │           │           │
             └───────────┼───────────┘
                         │
                         ▼
                  MySQL / Storage
```

Para cargas maiores, a arquitetura pode evoluir para serviços de computação e orquestração mais adequados a ambientes com alta demanda.

## Resiliência e recuperação

A estratégia de recuperação depende do componente e de sua configuração de redundância.

| Componente    | Estratégia               | Recuperação           |
| ------------- | ------------------------ | --------------------- |
| MySQL         | Backup automático        | Point in time restore |
| Blob Storage  | Redundância configurada  | Replicação            |
| Código fonte  | GitHub                   | Novo build            |
| Imagem Docker | Azure Container Registry | Novo deployment       |

O código fonte permanece no GitHub como fonte principal do projeto. A imagem pode ser reconstruída a partir do `Dockerfile` e publicada novamente no Azure Container Registry.

## Monitoramento de saúde

A aplicação disponibiliza o endpoint `GET /health` para verificar seu estado operacional.

Uma resposta esperada possui o formato:

```json
{
  "status": "healthy",
  "timestamp": "2026-08-20T10:30:00Z"
}
```

Esse endpoint pode ser utilizado por mecanismos de monitoramento e health checks para identificar indisponibilidade da aplicação.

O Application Insights complementa essa verificação acompanhando requisições, latência, erros e dependências.

Uma configuração de referência pode utilizar verificações a cada 30 segundos e alertas quando a taxa de erros ultrapassar um limite definido.

## Segurança

A arquitetura separa o acesso público da comunicação interna entre os serviços.

```text
Internet
   │
   │ HTTP :8000
   ▼
API / ACI
   │
   │ Comunicação privada
   ▼
MySQL

Administração
   │
   ├── Azure Portal
   └── Azure CLI
```

O endpoint da API é o único componente diretamente exposto ao cliente. O banco de dados deve permanecer restrito à rede e aos serviços que realmente necessitam de acesso.

As credenciais de acesso devem ser mantidas em mecanismos apropriados de gerenciamento de secrets, evitando sua exposição no código fonte, nas imagens Docker ou no repositório.

A comunicação com o banco utiliza SSL/TLS para proteger os dados durante o trânsito.

## Boas práticas adotadas

A arquitetura foi estruturada considerando separação de responsabilidades, armazenamento persistente, observabilidade e possibilidade de evolução da infraestrutura.

Os principais pontos são:

1. Aplicação isolada em container Docker.
2. Banco de dados gerenciado.
3. Armazenamento de arquivos separado da camada de aplicação.
4. Registry privado para imagens Docker.
5. Monitoramento centralizado.
6. Comunicação protegida com o banco de dados.
7. Credenciais mantidas fora do código fonte.
8. Código versionado no GitHub.
9. Endpoint dedicado para health check.
10. Possibilidade de evolução para múltiplas instâncias.

## Considerações finais

A arquitetura atual fornece uma base simples para execução da aplicação em ambiente Azure, mantendo separadas as responsabilidades de computação, persistência, armazenamento e observabilidade.

A solução pode ser expandida gradualmente conforme o volume de dados e requisições aumentar. Entre as principais possibilidades estão a utilização de múltiplas instâncias da API, adoção de um balanceador de carga, aumento da capacidade do banco e evolução para uma plataforma de orquestração de containers.

As configurações apresentadas neste documento representam a infraestrutura atual e devem ser revisadas sempre que houver alterações no ambiente, nos serviços utilizados ou nos requisitos de disponibilidade.
