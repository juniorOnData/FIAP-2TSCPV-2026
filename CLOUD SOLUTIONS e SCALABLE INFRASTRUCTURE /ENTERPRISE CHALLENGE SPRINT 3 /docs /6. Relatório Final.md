# Relatório Final

## Projeto NexusOps

**Disciplina:** Cloud Solutions & Scalable Infrastructure

**Mentor:** Rodrigo Katsumoto Sakai

**Data de entrega:** 30/08/2026

## Visão geral

O projeto teve como objetivo migrar o pipeline de análise de incidentes do Data Galaxy para uma arquitetura baseada em serviços Azure, utilizando computação em containers, banco de dados gerenciado, armazenamento de objetos e monitoramento centralizado.

A solução foi estruturada com FastAPI executando em Azure Container Instances, Azure Database for MySQL para persistência, Azure Blob Storage para armazenamento de arquivos e Azure Monitor, Log Analytics e Application Insights para observabilidade.

A arquitetura foi provisionada e validada com os principais fluxos da aplicação em funcionamento.

## Arquitetura

A solução final utiliza os seguintes componentes:

```text
                         Internet
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Azure Container      │
                 │ Instance            │
                 │                     │
                 │ FastAPI :8000       │
                 └──────────┬──────────┘
                            │
             ┌──────────────┼──────────────┐
             │              │              │
             ▼              ▼              ▼
         MySQL          Blob Storage    Monitoring
       db_nexusops       raw/processed   App Insights
                         logs/            Log Analytics
```

A aplicação está organizada na VNet `vnet-nexusops`, com separação entre `subnet-app` e `subnet-data`. O Azure Container Registry utilizado para armazenar a imagem está localizado em Norway East, enquanto os demais recursos principais estão em Chile Central.

## Modelo de Machine Learning

Existe uma ressalva importante em relação ao modelo utilizado pela aplicação.

O arquivo `modelo_incidentes.pkl` executado no ambiente foi gerado pelo script `treinar_modelo.py`, que utiliza regressão linear com lags e média móvel. Esse modelo foi utilizado para validar a integração entre a aplicação e a infraestrutura Cloud.

Ele **não corresponde ao modelo desenvolvido pela disciplina de Machine Learning** solicitado pelo enunciado.

Caso o time disponibilize o modelo oficial da disciplina, a substituição é direta: o arquivo pode ser atualizado, a imagem Docker reconstruída e o container recriado. Essa alteração não exige mudanças na arquitetura da solução.

Enquanto o modelo oficial não estiver disponível, o correto é considerar o modelo atual como **modelo equivalente utilizado para validação da integração**, mantendo a substituição como pendência conhecida.

Essa distinção é importante porque a infraestrutura e a integração foram validadas, mas isso não significa que o requisito referente ao modelo oficial de Machine Learning tenha sido atendido integralmente.

## Desempenho do modelo

Durante o treinamento do modelo utilizado na validação foi obtido:

```text
R² no teste: -1.208
```

O valor negativo indica que, nesse conjunto de teste, o modelo apresentou desempenho inferior ao uso da média como referência.

Esse resultado deve ser interpretado considerando o tamanho reduzido da amostra, que contém apenas 30 registros. A métrica não invalida a implementação da infraestrutura, pois o objetivo desta entrega é demonstrar a arquitetura Cloud e sua integração com a aplicação.

Entretanto, caso a métrica seja apresentada na avaliação, ela deve ser mencionada de forma transparente, sem atribuir ao modelo uma capacidade preditiva que os testes não demonstraram.

## Principais desafios

A execução apresentou alguns desafios relacionados principalmente às características da subscription Azure for Students.

A disponibilidade regional exigiu a utilização de Chile Central para os recursos principais e Norway East para o processo de build do ACR.

A criação do MySQL apresentou instabilidade durante o provisionamento, exigindo novas tentativas.

Também houve limitações na configuração de regras de firewall pela CLI, sendo necessário utilizar o Portal Azure em alguns momentos.

Outro ponto foi o gerenciamento das variáveis de ambiente do ACI, já que alterações relevantes exigiram a recriação do container.

Esses problemas reforçaram a importância de manter alternativas de provisionamento e utilizar conjuntamente Azure CLI e Portal quando necessário.

## Observabilidade

A observabilidade foi implementada desde a execução inicial da aplicação.

O Log Analytics centraliza os logs, o Application Insights acompanha a telemetria da aplicação e o Azure Monitor fornece métricas e alertas de infraestrutura.

Essa estrutura foi utilizada tanto para acompanhamento do ambiente quanto para diagnóstico dos problemas encontrados durante a implementação.

## Próximos passos

A solução atual atende ao objetivo de demonstrar a execução do pipeline em uma infraestrutura Cloud baseada em Azure.

Para uma evolução do ambiente, os principais pontos são:

1. Substituição do modelo de fallback pelo modelo oficial da disciplina de Machine Learning.

2. Utilização de Azure Key Vault para gerenciamento de credenciais.

3. Ativação de HTTPS na API.

4. Restrição do acesso ao banco por meio de recursos de rede privada.

5. Evolução da disponibilidade e resiliência do banco.

6. Implementação de CI/CD com GitHub Actions.

7. Ampliação dos testes automatizados e testes de carga.

Esses pontos representam evolução da solução e não fazem parte da configuração mínima utilizada para validar a arquitetura atual.

## Conclusão

A implementação demonstrou a migração do pipeline de incidentes para uma arquitetura Cloud utilizando serviços gerenciados da Azure.

A aplicação foi containerizada, publicada no Azure Container Instances, integrada ao MySQL e ao Blob Storage e conectada a uma camada centralizada de observabilidade. Os principais endpoints foram executados com sucesso e os dados gerados foram persistidos e consultados no banco.

A principal pendência identificada está relacionada ao modelo de Machine Learning. O modelo atualmente executado foi desenvolvido especificamente para validar a integração da aplicação e deve ser substituído pelo modelo oficial da disciplina quando disponibilizado.

Do ponto de vista de Cloud Solutions, a implementação demonstra a integração entre computação, persistência, armazenamento, rede, observabilidade e operação em um ambiente Azure.
