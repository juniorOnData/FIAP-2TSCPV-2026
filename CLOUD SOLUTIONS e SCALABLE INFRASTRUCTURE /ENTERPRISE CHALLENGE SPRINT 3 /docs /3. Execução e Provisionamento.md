# Execução e Provisionamento da Infraestrutura

## Visão geral

A infraestrutura foi provisionada na Microsoft Azure utilizando Azure CLI, com a aplicação posteriormente empacotada em Docker e executada no Azure Container Instances.

A execução contemplou a criação da rede, armazenamento, banco de dados, registry da imagem, ambiente de execução e camada de monitoramento. Ao final, a aplicação foi validada por meio dos principais endpoints e consultas ao banco.

O ambiente utiliza **Chile Central** como região principal e **Norway East** para o processo de build do Azure Container Registry, devido às restrições da subscription utilizada.

## Preparação do ambiente

A execução foi realizada com Azure CLI utilizando a subscription **Azure for Students**.

As principais variáveis utilizadas durante o provisionamento foram:

```bash
SUBSCRIPTION_ID="<subscription-id>"
LOCATION="chilecentral"
LOCATION_BUILD="norwayeast"
RG_NAME="rg-nexusops-locaweb"
RANDOM_ID="8929"
```

Após a autenticação com `az login`, a subscription foi definida para o ambiente utilizado.

```bash
az login
az account set --subscription "Azure for Students"
```

## Resource Group

O primeiro recurso criado foi o Resource Group `rg-nexusops-locaweb`, utilizado para organizar os componentes da solução.

```bash
az group create \
  --name $RG_NAME \
  --location $LOCATION
```

A partir desse ponto, os demais recursos foram associados ao mesmo Resource Group.

## Rede

A comunicação dos recursos foi organizada na VNet `vnet-nexusops`, utilizando o espaço `10.0.0.0/16`.

Foram definidas duas subnets, separando a aplicação dos recursos de dados:

```text
vnet-nexusops
│
├── subnet-app
│   └── 10.0.1.0/24
│
└── subnet-data
    └── 10.0.2.0/24
```

A criação da VNet e das subnets foi realizada diretamente pelo Azure CLI.

## Armazenamento

O armazenamento dos arquivos da aplicação foi configurado em um Storage Account do tipo `StorageV2`, com tier `Hot` e replicação `GRS`.

```text
stnexusops8929
│
├── raw
├── processed
└── logs
```

Os containers foram utilizados para separar arquivos de entrada, resultados processados e logs da aplicação.

A configuração principal foi:

```bash
az storage account create \
  --name stnexusops${RANDOM_ID} \
  --resource-group $RG_NAME \
  --location $LOCATION \
  --kind StorageV2 \
  --sku Standard_GRS \
  --access-tier Hot
```

## Banco de dados

O banco foi provisionado utilizando Azure Database for MySQL, com 1 vCore, 50 GB de armazenamento e MySQL 8.0.

```text
Servidor: mysql-nexusops-8929
Database: db_nexusops
Região: Chile Central
```

A estrutura inicial foi composta pelas tabelas `tb_previsoes` e `tb_auditoria`, utilizadas respectivamente para armazenar previsões e informações de auditoria.

O acesso ao servidor foi configurado por meio das regras de firewall da Azure. Durante a execução, o SSL foi temporariamente desabilitado para facilitar os testes de conectividade, configuração que não deve ser mantida em um ambiente de produção.

O schema utilizado foi:

```sql
CREATE TABLE tb_previsoes (
    id INT PRIMARY KEY AUTO_INCREMENT,
    data_previsao DATETIME NOT NULL,
    d_plus_1 FLOAT NOT NULL,
    d_plus_7 FLOAT NOT NULL,
    registros_ingeridos INT NOT NULL,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE tb_auditoria (
    id INT PRIMARY KEY AUTO_INCREMENT,
    operacao VARCHAR(50) NOT NULL,
    qtd_registros INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    mensagem TEXT,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## Container Registry

A imagem Docker da aplicação foi armazenada no Azure Container Registry `acrnexusops8929`.

O registry foi criado em **Norway East**, enquanto os demais recursos permaneceram em Chile Central.

```text
acrnexusops8929.azurecr.io
└── nexusops-api:latest
```

A imagem foi construída diretamente no ambiente Azure utilizando `az acr build`, evitando a necessidade de um Docker Engine local.

```bash
az acr build \
  --registry $ACR_NAME \
  --image nexusops-api:latest \
  --file docker/Dockerfile .
```

Após o build, o repositório e a tag `latest` foram verificados no registry.

## Execução da aplicação

Com a imagem disponível no registry, a aplicação foi executada no Azure Container Instance `aci-nexusops-api`.

A instância foi configurada com:

```text
CPU: 1 vCPU
Memória: 1 GB
Porta: 8000
Sistema: Linux
```

As configurações de banco e armazenamento foram fornecidas por variáveis de ambiente durante a criação do container.

```bash
az container create \
  --name aci-nexusops-api \
  --resource-group $RG_NAME \
  --image $ACR_REGISTRY/nexusops-api:latest \
  --cpu 1 \
  --memory 1 \
  --port 8000 \
  --protocol TCP \
  --dns-name-label nexusops-api-${RANDOM_ID}
```

Após a inicialização, o FQDN público da aplicação foi obtido diretamente pelo Azure CLI.

```bash
ACI_FQDN=$(az container show \
  --resource-group $RG_NAME \
  --name aci-nexusops-api \
  --query ipAddress.fqdn -o tsv)
```

A aplicação ficou disponível em:

```text
http://nexusops-api-8929.chilecentral.azurecontainer.io:8000
```

Os logs do container foram utilizados para confirmar a inicialização do servidor e o funcionamento da aplicação.

## Monitoramento

A camada de observabilidade foi configurada após a publicação da aplicação.

Foi criado o workspace `law-nexusops` no Log Analytics, seguido pela criação do Application Insights `appi-nexusops`.

```text
law-nexusops
    │
    └── appi-nexusops
            │
            └── Application telemetry
```

Os logs do Azure Container Instance foram direcionados para o Log Analytics por meio de Diagnostic Settings.

A consulta utilizada para validar os logs foi:

```kusto
ContainerInstanceLog_CL
| where TimeGenerated > ago(1h)
| order by TimeGenerated desc
| project TimeGenerated, LogLevel, Message=Log_s
```

Essa etapa confirmou a disponibilidade dos registros da aplicação no ambiente de monitoramento.

## Validação da aplicação

Após a infraestrutura estar disponível, foram realizados testes nos principais fluxos da API.

### Health check

O endpoint `/health` foi utilizado para confirmar que a aplicação estava respondendo corretamente.

```bash
curl -X GET "${API_URL}/health"
```

### Ingestão

Foi utilizado um CSV de teste contendo três registros de incidentes. O arquivo foi enviado para o endpoint `/ingerir`:

```bash
curl -X POST "${API_URL}/ingerir" \
  -H "Content-Type: multipart/form-data" \
  -F "file=@data/test_incidentes.csv"
```

A API retornou sucesso e confirmou a ingestão dos três registros.

### Previsão

O endpoint `/prever` foi executado após a ingestão dos dados:

```bash
curl -X GET "${API_URL}/prever"
```

A resposta retornou os valores calculados para D+1 e D+7.

### Consulta

Os resultados armazenados foram consultados por meio do endpoint `/previsoes`:

```bash
curl -X GET "${API_URL}/previsoes"
```

A consulta retornou os registros persistidos no banco, incluindo os valores de previsão e a quantidade de registros ingeridos.

Por fim, a persistência foi confirmada diretamente no MySQL:

```sql
SELECT COUNT(*) AS total_previsoes
FROM tb_previsoes;

SELECT *
FROM tb_previsoes
ORDER BY criado_em DESC
LIMIT 5;
```
