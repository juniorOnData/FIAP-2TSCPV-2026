# Monitoramento, Logs e Métricas

## Visão geral

A observabilidade da aplicação foi estruturada utilizando Azure Monitor, Log Analytics e Application Insights.

A camada de monitoramento acompanha infraestrutura, API, banco de dados e eventos da aplicação. O objetivo é identificar degradação de desempenho, erros e indisponibilidade, mantendo os principais registros centralizados.

## Indicadores acompanhados

| Camada        | Indicadores                         |
| ------------- | ----------------------------------- |
| Aplicação     | CPU, memória e requisições          |
| API           | Latência, status HTTP e erros       |
| Banco         | Conexões e desempenho               |
| Armazenamento | Uso e operações de I/O              |
| Negócio       | Dados ingeridos e previsões geradas |

Os principais limites utilizados como referência são CPU acima de 80%, memória acima de 85%, taxa de erros acima de 5% e latência superior a 2 segundos.

## Azure Monitor

O Azure Monitor é responsável pelas métricas de infraestrutura do Azure Container Instance.

Entre os indicadores acompanhados estão:

```text
CPU Usage Percentage
Memory Usage Percentage
Network In Bytes
Network Out Bytes
```

As métricas também podem ser consultadas pelo Azure CLI. Um exemplo utilizado durante a análise foi a consulta de CPU:

```bash
az monitor metrics list \
  --resource /subscriptions/${SUBSCRIPTION_ID}/resourceGroups/${RG_NAME}/providers/Microsoft.ContainerInstance/containerGroups/aci-nexusops-api \
  --metric CPUUsage \
  --interval PT1M \
  --aggregation Average
```

Um alerta de CPU foi configurado considerando utilização superior a 80% durante uma janela de cinco minutos.

## Log Analytics

O workspace `law-nexusops` concentra os logs utilizados para análise da aplicação e da infraestrutura.

A consulta abaixo permite visualizar os registros mais recentes:

```kusto
ContainerInstanceLog_CL
| where TimeGenerated > ago(1h)
| order by TimeGenerated desc
| project TimeGenerated, LogLevel_s, Message=Log_s
| limit 50
```

Para identificar erros recentes:

```kusto
ContainerInstanceLog_CL
| where LogLevel_s in ("ERROR", "CRITICAL")
| where TimeGenerated > ago(24h)
| summarize Count=count() by LogLevel_s, bin(TimeGenerated, 1h)
| order by TimeGenerated desc
```

Também é possível acompanhar a quantidade de requisições ao longo do tempo:

```kusto
AppServiceHTTPLogs_CL
| where TimeGenerated > ago(1h)
| summarize Requests=count() by bin(TimeGenerated, 1m)
| render timechart
```

Essas consultas foram utilizadas para acompanhar comportamento da aplicação, volume de requisições e ocorrência de erros.

## Application Insights

O Application Insights `appi-nexusops` concentra a telemetria da aplicação.

A instrumentação registra requisições HTTP, latência, erros e dependências, permitindo acompanhar o comportamento da API e suas interações com o banco de dados.

A aplicação utiliza `AzureLogHandler` para encaminhar os registros:

```python
import logging
from opencensus.ext.azure.log_exporter import AzureLogHandler

instrumentation_key = os.getenv("APPINSIGHTS_INSTRUMENTATIONKEY")

logging.getLogger().addHandler(
    AzureLogHandler(
        connection_string=f"InstrumentationKey={instrumentation_key}"
    )
)
```

Os eventos de negócio também podem ser registrados diretamente na aplicação. Na ingestão, por exemplo, são registrados o início da operação, sua conclusão e eventuais exceções.

```python
logger.info(f"Iniciando ingestão do arquivo: {file.filename}")

try:
    # processamento
    logger.info(f"Ingestão concluída: {qtd} registros")
except Exception as exc:
    logger.error(f"Erro na ingestão: {exc}", exc_info=True)
    raise
```

A análise da telemetria é realizada principalmente pelas áreas de Performance e Transaction Search do Application Insights.

## Alertas

Os alertas foram organizados a partir dos principais sinais de degradação da infraestrutura.

| Alerta             | Condição de referência       |
| ------------------ | ---------------------------- |
| CPU alta           | CPU > 80% por 5 minutos      |
| Erros elevados     | Mais de 10 falhas no período |
| Banco indisponível | Ausência de conexões ativas  |

Um Action Group foi utilizado como mecanismo de notificação, permitindo centralizar os destinatários dos alertas.

## Auditoria

Além da telemetria da aplicação, o Azure Activity Log foi utilizado para acompanhar alterações realizadas nos recursos do Resource Group.

A consulta utilizada para analisar as atividades recentes foi:

```bash
az monitor activity-log list \
  --resource-group $RG_NAME \
  --offset 24h \
  --output table
```

Os registros também podem ser exportados para análise posterior:

```bash
az monitor activity-log list \
  --resource-group $RG_NAME \
  --offset 30d \
  --output json > activity-log-30-days.json
```

Essa camada complementa os logs da aplicação ao registrar operações realizadas na própria infraestrutura Azure.

## Troubleshooting

O monitoramento também foi utilizado como apoio à investigação de problemas.

Para identificar erros recentes da aplicação:

```kusto
ContainerInstanceLog_CL
| where LogLevel_s in ("ERROR", "CRITICAL")
| order by TimeGenerated desc
| limit 20
```

Para investigar possíveis problemas de desempenho na ingestão:

```kusto
AppServiceHTTPLogs_CL
| where Endpoint == "POST /ingerir"
| summarize Avg=avg(totaltimems),
            Max=max(totaltimems),
            Count=count()
    by bin(TimeGenerated, 5m)
| where Avg > 1000
```

Em casos de falha de conexão com o banco, a conectividade entre a aplicação e o MySQL pode ser validada diretamente a partir do container.
