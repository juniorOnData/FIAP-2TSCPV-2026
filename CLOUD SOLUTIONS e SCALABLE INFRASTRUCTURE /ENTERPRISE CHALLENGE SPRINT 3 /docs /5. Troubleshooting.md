# Troubleshooting

Durante o provisionamento e a execução da infraestrutura Azure foram identificados alguns problemas relacionados a restrições da subscription, conectividade, containerização, banco de dados e configuração da aplicação.

Este documento reúne os principais cenários encontrados e as soluções utilizadas ou consideradas durante a execução.

## Regiões não autorizadas

### Sintoma

Ao criar um recurso, a Azure pode retornar uma mensagem indicando que a subscription não possui permissão para utilizar determinada região.

```text
The subscription does not have permissions
to create resources in region 'chilecentral'
```

### Causa

A subscription **Azure for Students** possui restrições de região.

Entre as regiões disponíveis para o ambiente estavam `chilecentral`, `norwayeast`, `germanywestcentral`, `switzerlandnorth` e `italynorth`.

A disponibilidade pode ser consultada diretamente pela CLI:

```bash
az account list-locations \
  --query "[].{Name:name, DisplayName:displayName}" \
  -o table
```

Quando necessário, a região utilizada no provisionamento pode ser alterada:

```bash
export LOCATION="norwayeast"
```

## Falha na criação do MySQL

### Sintoma

Durante a criação do servidor MySQL ocorreu uma falha de operação de longa duração:

```text
Long running operation failed with status 'InternalServerError'
```

### Causa

O problema foi associado à disponibilidade do serviço dentro da subscription utilizada.

A criação foi novamente executada pela CLI e, quando necessário, realizada pelo Portal Azure. A criação do servidor pode levar alguns minutos até que o recurso esteja disponível.

A configuração utilizada foi:

```bash
az mysql server create \
  --name mysql-nexusops-${RANDOM_ID} \
  --resource-group $RG_NAME \
  --location $LOCATION \
  --admin-user azureuser \
  --admin-password $DB_PASSWORD \
  --sku-name B_Gen5_1 \
  --storage-size 51200 \
  --version 8.0
```

## Erro na regra de firewall do MySQL

### Sintoma

A criação da regra de firewall pode retornar:

```text
Firewall rule creation failed with InternalServerError
```

### Solução

Quando a criação pela CLI apresentou falha, a configuração foi realizada pelo Portal Azure em **Connection Security** e **Firewall Rules**.

Também foi considerada a criação via CLI:

```bash
az mysql server firewall-rule create \
  --resource-group $RG_NAME \
  --server-name mysql-nexusops-${RANDOM_ID} \
  --name AllowAllAzureIps \
  --start-ip-address 0.0.0.0 \
  --end-ip-address 0.0.0.0
```

A alternativa mais restritiva é utilizar o IP da própria ACI como origem da regra.

## ACI sem conexão com MySQL

### Sintoma

A aplicação apresentou erro ao tentar estabelecer conexão com o banco:

```text
Lost connection to MySQL server
```

### Causa

O firewall do MySQL pode bloquear o endereço utilizado pela ACI.

O IP público da instância pode ser obtido com:

```bash
ACI_IP=$(az container show \
  --resource-group $RG_NAME \
  --name aci-nexusops-api \
  --query ipAddress.ip \
  -o tsv)
```

A partir desse endereço, foi possível criar uma regra específica de acesso ao banco:

```bash
az mysql server firewall-rule create \
  --resource-group $RG_NAME \
  --server-name mysql-nexusops-${RANDOM_ID} \
  --name AllowACI \
  --start-ip-address $ACI_IP \
  --end-ip-address $ACI_IP
```

A conectividade foi validada executando uma consulta simples ao MySQL a partir do container.

## Falha no build da imagem Docker

### Sintoma

O build realizado pelo ACR apresentou erro de módulo Python ausente:

```text
ModuleNotFoundError: No module named 'fastapi'
```

### Causa

O `requirements.txt` não estava sendo copiado ou instalado corretamente durante a construção da imagem.

O Dockerfile utilizado deve instalar as dependências antes de copiar o código da aplicação:

```dockerfile
FROM python:3.9-slim

WORKDIR /app

COPY src/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ .

EXPOSE 8000

CMD [
  "gunicorn",
  "app:app",
  "--workers", "4",
  "--worker-class", "uvicorn.workers.UvicornWorker"
]
```

O build também pode ser validado localmente antes do envio ao ACR:

```bash
docker build \
  -f docker/Dockerfile \
  -t nexusops-api:test .

docker run \
  -p 8000:8000 \
  nexusops-api:test

curl http://localhost:8000/health
```

## ACI sem resposta

### Sintoma

A API pode apresentar timeout durante uma requisição:

```text
curl: (28) Operation timed out
```

### Diagnóstico

O primeiro ponto de análise são os logs do container:

```bash
az container logs \
  --resource-group $RG_NAME \
  --name aci-nexusops-api \
  --follow
```

Os principais sinais observados são:

```text
Uvicorn running on
Traceback
killed
```

O primeiro indica inicialização do servidor. `Traceback` aponta para uma exceção durante a execução e `killed` pode indicar insuficiência de memória.

Caso os recursos atuais sejam insuficientes, a ACI pode ser recriada com maior capacidade.

## Falha de autenticação no ACR

### Sintoma

A ACI não consegue baixar a imagem do registry:

```text
401: authentication required
```

### Causa

As credenciais utilizadas para acessar o Azure Container Registry podem estar incorretas ou desatualizadas.

As credenciais podem ser consultadas novamente:

```bash
ACR_USERNAME=$(az acr credential show \
  --resource-group $RG_NAME \
  --name acrnexusops8929 \
  --query username \
  -o tsv)

ACR_PASSWORD=$(az acr credential show \
  --resource-group $RG_NAME \
  --name acrnexusops8929 \
  --query "passwords[0].value" \
  -o tsv)
```

Após atualizar as credenciais, a instância pode ser recriada utilizando os novos valores.

## Upload de CSV muito grande

### Sintoma

Arquivos maiores podem resultar em:

```text
413: Request Entity Too Large
```

### Tratamento

A aplicação realiza validação do tamanho do arquivo antes do processamento.

Um limite de referência de 100 MB foi considerado:

```python
contents = await file.read()

if len(contents) > 100 * 1024 * 1024:
    return {
        "error": "Arquivo muito grande",
        "max": "100 MB"
    }
```

Para arquivos significativamente maiores, o processamento direto pela API deixa de ser a melhor abordagem. Nesse cenário, o Blob Storage pode ser utilizado como ponto de entrada para o processamento assíncrono.

## Erro de encoding no MySQL

### Sintoma

A inserção de registros com caracteres especiais pode apresentar:

```text
Incorrect string value for column 'mensagem'
```

### Causa

O problema está relacionado à configuração de charset da conexão ou das tabelas.

A aplicação utiliza `utf8mb4` na conexão:

```python
connection = pymysql.connect(
    host=os.getenv("DB_HOST"),
    user=os.getenv("DB_USER"),
    password=os.getenv("DB_PASSWORD"),
    database=os.getenv("DB_NAME"),
    charset="utf8mb4",
    cursorclass=pymysql.cursors.DictCursor
)
```

As tabelas também podem ser convertidas para `utf8mb4`:

```sql
ALTER TABLE tb_previsoes
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

ALTER TABLE tb_auditoria
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

## Modelo de machine learning não encontrado

### Sintoma

O endpoint `/prever` pode falhar quando o arquivo do modelo não está presente no container:

```text
FileNotFoundError:
No such file or directory: 'modelo_incidentes.pkl'
```

### Causa

O modelo não foi incluído na imagem Docker ou não foi gerado antes da execução da aplicação.

Uma das soluções consideradas foi incluir o modelo diretamente na imagem:

```dockerfile
COPY src/models/modelo_incidentes.pkl ./models/
```

Outra possibilidade é utilizar o script de treinamento existente no projeto:

```bash
python scripts/treinar_modelo.py
```

A abordagem adotada depende da forma como o modelo é gerenciado no ciclo de execução da aplicação.

## Application Insights sem chave de instrumentação

### Sintoma

A aplicação pode apresentar erro ao iniciar a integração com o Application Insights:

```text
KeyError: 'APPINSIGHTS_INSTRUMENTATIONKEY'
```

### Causa

A variável de ambiente não foi disponibilizada para o container.

A chave pode ser recuperada pelo Azure CLI:

```bash
APPINSIGHTS_KEY=$(az monitor app-insights component show \
  --app appi-nexusops \
  --resource-group $RG_NAME \
  --query instrumentationKey \
  -o tsv)
```

Depois disso, a variável deve ser disponibilizada para a aplicação durante a criação ou atualização da ACI.

## Diagnóstico geral

Quando a aplicação apresenta comportamento inesperado, a investigação segue uma sequência simples:

```text
Health check
    │
    ▼
Logs da ACI
    │
    ▼
Variáveis de ambiente
    │
    ▼
Conectividade com MySQL
    │
    ▼
Firewall
    │
    ▼
Application Insights
    │
    ▼
CPU e memória
```

Os comandos mais utilizados durante esse processo são:

```bash
curl http://<api>:8000/health

az container logs \
  --name aci-nexusops-api \
  --resource-group $RG_NAME

az container show \
  --name aci-nexusops-api \
  --resource-group $RG_NAME

az container restart \
  --name aci-nexusops-api \
  --resource-group $RG_NAME
```

A análise parte do estado da aplicação e dos logs antes de considerar alterações de infraestrutura ou a recriação do container.

## Conclusão

Os problemas encontrados durante a execução estiveram principalmente relacionados às restrições da subscription, disponibilidade dos serviços, regras de firewall, autenticação do registry e configuração do container.

A centralização dos logs e métricas em Azure Monitor, Log Analytics e Application Insights tornou a identificação desses problemas mais direta e forneceu uma base para diagnóstico das próximas execuções.
